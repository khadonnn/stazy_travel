## 1. EXECUTIVE SUMMARY

The Stazy Hotel system is a microservices-based hotel booking platform consisting of **8 services**: Admin (Next.js), Client (Next.js), Booking (Fastify), Payment (Hono), Email (HTTP), Gateway, Product (Express), Search (FastAPI), and Socket. Communication is primarily event-driven via Apache Kafka, with Redis + BullMQ providing background job processing and Saga timeout management.

**Architecture Classification: Hybrid (Choreography with Orchestration-like elements)**

The system implements **choreography-based saga** via Kafka events with **no central orchestrator**. However, BullMQ's `saga-timeout` queue acts as an orchestration-like timeout manager. The Booking Service acts as a de facto saga coordinator by maintaining the saga-timeout queue and processing booking-events/payment-events.

**Key Strengths:**

- Transactional Outbox pattern for event publishing
- Idempotency at multiple layers
- Redis-based room hold + Redlock for concurrency control
- Graceful shutdown handling across services
- Dedicated DLQ (Dead Letter Queue) for payment and email failures

**Critical Weaknesses:**

- **Stripe webhook bypasses Outbox** – directly publishes to Kafka (data loss risk)
- **In-memory idempotency cache** – not distributed, fails under multi-instance deployment
- **Dual database** (PostgreSQL + MongoDB) with overlapping Booking models
- **Shared PostgreSQL database** across all services (tight coupling)
- **No explicit compensating transaction framework** – compensation is ad-hoc in workers
- **Payment service's `sendBookingEvent` wrapper is broken** – incorrect Kafka API usage
- **No timeout recovery mechanism** for service crashes mid-saga

### B. Is There a Central Saga Orchestrator?

**No.** There is no dedicated Saga Orchestrator service, no Workflow Manager, and no State Machine library. The pattern is **choreography-based saga** with these characteristics:

- **No Saga Coordinator class/file exists** – searched entire codebase
- **No state machine engine** (e.g., XState, Temporal) – not found
- **Booking Service does not directly control Payment Service** – communicates via Kafka events
- **No central workflow definition** – saga flow is distributed across services

### C. Orchestration-like Elements (Why Hybrid)

Despite being choreography-dominant, the system has orchestration-like characteristics:

1. **BullMQ `saga-timeout` Queue (Booking Service)** – `apps/booking-service/src/queues/saga-timeout.queue.ts`
   - Booking Service creates a delayed job when booking is created (15-minute timeout)
   - This acts as a de facto timeout orchestrator
   - The worker checks booking status and performs compensation (cancellation)

2. **Booking Service as de facto saga coordinator**:
   - Hosts both `saga-timeout` queue and `booking-events` queue workers
   - Consumes both `booking-events` and `payment-events` Kafka topics
   - Processes payment success and failure events
   - Performs compensation (cancellation) on failures and timeouts

```
- File: apps/payment-service/src/routes/webhooks.route.ts:96-101

```

```
- File: utils/booking.ts:153-179

- BUT: no idempotency for the Kafka send → potential duplicate events

- ❌ These messages will never be published
```

## 6. TRANSACTIONAL OUTBOX ANALYSIS

### Outbox Implementation

**Schema:** `packages/product-db/generated/prisma/models/OutboxMessage.ts`

- Table: `OutboxMessage`
- Key fields: `id` (UUID), `dedupKey` (unique), `aggregateType`, `aggregateId`, `eventType`, `topic`, `payload` (JSON), `status` (PENDING/PROCESSING/SENT/FAILED), `attempts`, `availableAt`, `lastError`
- **Unique constraint on `dedupKey`** – prevents duplicate outbox entries

**Outbox Producer (Booking Service):**

- File: `apps/booking-service/src/utils/booking.ts:128-138`
- `BOOKING_CREATED` event written inside Prisma `$transaction` alongside `booking.create`
- Dedup key: `booking:{bookingId}:BOOKING_CREATED`
- ✅ Business data and outbox record saved in same DB transaction

**Outbox Producer (Payment Service):**

- File: `apps/payment-service/src/queues/payment.queue.ts:177-196`
- `PAYMENT_SUCCESS` event written inside Prisma `$transaction`
- Inside BullMQ worker (idempotent)
- ✅ Same transaction pattern

**Outbox Producer (Booking Service - Compensation):**

- File: `apps/booking-service/src/utils/booking.ts:377-394`
- `BOOKING_CANCELLED_PAYMENT_FAILED` inside Prisma `$transaction`
- ✅ Same transaction pattern

**Outbox Worker:**

- File: `apps/booking-service/src/workers/outbox-worker.ts`
- Poll-based (every 5 seconds, configurable)
- Claim-check pattern: `PENDING → PROCESSING` via `updateMany`
- Batch size: 20 (configurable)
- Max attempts: 5 (configurable)
- Retry delay: 3 seconds (configurable)

### Outbox Flow

```
1. Business transaction writes to outboxMessage (PENDING)
2. Outbox worker polls for PENDING messages
3. Claims messages: UPDATE status = PROCESSING (atomic)
4. For each message: producer.send(topic, payload)
5. On success: UPDATE status = SENT
6. On failure: UPDATE status = PENDING (or FAILED after max attempts)
```

### Verification Questions

**Q1: Is the Transactional Outbox Pattern correctly implemented?**
✅ **Yes, for most cases.** The Booking Service correctly writes business data and outbox records in the same Prisma `$transaction`. Key evidence:

- `utils/booking.ts:83-144` – booking.create + outboxMessage.create in single $transaction
- `utils/booking.ts:359-394` – booking.update + outboxMessage.create in single $transaction
- `queues/saga-timeout.queue.ts:156-193` – booking.update + outboxMessage.create in single $transaction

❌ **No, for Stripe webhook.** The Payment Service webhook (`webhooks.route.ts:91`) sends directly to Kafka, completely bypassing the outbox pattern. This is the single most critical architectural gap.

**Q2: Are business data and outbox records saved in the same database transaction?**
✅ **Yes, for all Booking Service operations.** All three outbox producers use `prisma.$transaction()`.

**Q3: Is duplicate event protection implemented?**
✅ **Yes, via dedupKey unique constraint.** OutboxMessage.dedupKey has a unique constraint, preventing duplicate outbox entries from the same event.
✅ **Yes, via ProcessedEvent.** The booking-events worker uses `INSERT ... ON CONFLICT (eventId) DO NOTHING` for deduplication at consumer side (`booking-events.queue.ts:69-81`).

**Q4: Is idempotency implemented?**
⚠️ **Partially.**

- **In-memory cache** (`packages/bullmq/src/idempotency.ts`) – uses JavaScript `Map` object
  - ❌ Not distributed – each service instance has its own cache
  - ❌ Cache TTL is 1 hour (hardcoded)
  - ✅ Key scheme is well-designed: `saga:{bookingId}:{requestId}`, `payment:{bookingId}:{transactionId}`, `email:{messageId}:{emailType}:{attemptCount}`
- **ProcessedEvent table** – proper database-level dedup using `ON CONFLICT`
- **Outbox dedupKey** – proper unique constraint
- No Redis-backed distributed idempotency

### Q1: Are services using a Shared Database?

- `packages/product-db/src/index.ts` – Exports the same `prisma` instance
- `packages/product-db/src/client.ts` – Singleton `PrismaClient` with PostgreSQL adapter
- Both Booking Service and Payment Service import from `@repo/product-db`
- The shared database contains: `Booking`, `Hotel`, `User`, `OutboxMessage`, `ProcessedEvent`, `DailyStat`, etc. in the same schema

**File Evidence:**

- `apps/booking-service/src/utils/booking.ts:4` – `import { prisma } from "@repo/product-db"`

- `apps/payment-service/src/queues/payment.queue.ts:26` – `import { prisma } from "@repo/product-db"`

### Q2: Are services isolated by schema or tables?

❌ **No schema or table isolation.** All services operate on the same tables in the same PostgreSQL database. There is no schema-level separation, no database-per-service, and no ownership boundaries.

### Q3: Is Database-per-Service implemented?

❌ **No.** The system uses a monolith database approach with a single PostgreSQL instance shared across services. This creates tight coupling:

- Booking Service writes to `Booking` table
- Payment Service also writes to `Booking` table (via `updateBookingStatusToPaid`)
- Both services read/write same `OutboxMessage` table
- Both services use same `ProcessedEvent` table

### Q4: What coupling risks currently exist?

**High Risk:** Booking Service and Payment Service both directly modify the `Booking` table

- `apps/booking-service/src/queues/booking-events.queue.ts:165-173` – Booking Worker updates booking status
- `apps/payment-service/src/queues/payment.queue.ts:177-196` – Payment Worker creates outbox events (reads booking indirectly)
- If Booking Service schema changes, Payment Service breaks

**Medium Risk:** Dual database (MongoDB + PostgreSQL)

- `packages/booking-db/src/booking-model.ts` – Mongoose Booking model (legacy)
- `packages/product-db/generated/prisma/models/Booking.ts` – Prisma Booking model (current)
- The analytics cron job (`apps/booking-service/src/cron/analyticsJob.ts:62`) still queries MongoDB (`Booking.aggregate()`) while business logic uses PostgreSQL
- Data inconsistency between MongoDB and PostgreSQL is possible

**Medium Risk:** Admin and Client apps import database stubs

- `apps/admin/src/stubs/booking-db-stub.ts`, `apps/admin/src/stubs/product-db-stub.ts`
- `apps/client/src/stubs/product-db-stub.ts`
- These stubs suggest frontend code directly accesses databases

## 8. RISKS & FINDINGS

### RISK 1: Stripe Webhook Bypasses Transactional Outbox

| Attribute           | Value                                                                                                                                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Severity**        | **🔴 HIGH**                                                                                                                                                                                                                                                                          |
| **Evidence**        | `apps/payment-service/src/routes/webhooks.route.ts:91` – `await producer.send("booking-events", kafkaPayload)` directly publishes to Kafka without going through the outbox pattern.                                                                                                 |
| **Impact**          | If Kafka is unavailable during webhook processing, the payment success/failure message is **permanently lost**. Stripe will retry the webhook, but there is no idempotency for the Kafka send, so duplicate processing is possible.                                                  |
| **Recommended Fix** | Instead of direct `producer.send()`, write the webhook event to the outbox table in PostgreSQL: insert a row into `outboxMessage` table with `topic: "booking-events"`. The existing Outbox Worker will pick it up and publish to Kafka reliably. Add idempotency webhook event IDs. |

### RISK 2: In-Memory Idempotency Cache Not Distributed

| Attribute           | Value                                                                                                                                                                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Severity**        | **🔴 HIGH**                                                                                                                                                                                                                                                                    |
| **Evidence**        | `packages/bullmq/src/idempotency.ts:51` – `const idempotencyCache = new Map<string, IdempotencyRecord>()` is an in-memory JavaScript Map. The code comment on line 55-56 states: "In production, use Redis for distributed cache."                                             |
| **Impact**          | When multiple instances of Booking Service or Payment Service run, each instance has its own idempotency cache. A saga timeout job could be processed by two different instances, both passing the idempotency check, leading to duplicate compensation (double cancellation). |
| **Recommended Fix** | Replace the in-memory Map with Redis-backed storage using the existing `@repo/redis` package. Implement `SET key EX 3600 NX` for distributed idempotency checks.                                                                                                               |

### RISK 3: Missing Timeout Job Recovery (Saga Timeout)

| Attribute           | Value                                                                                                                                                                                                                                                                                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🔴 HIGH**                                                                                                                                                                                                                                                                                                                                                    |
| **Evidence**        | `apps/booking-service/src/utils/booking.ts:173-178` – If BullMQ `sagaTimeoutQueue.add()` fails, the code catches the error and continues without the timeout job: `"Continuing without timeout..."`. Additionally, `booking-events.queue.ts:125-134` removes the timeout job but there is no periodic scan for bookings stuck in PENDING without timeout jobs. |
| **Impact**          | If the saga-timeout job fails to be created (e.g., Redis transient error), or if the service crashes before creating it, the booking remains in PENDING state forever. No automatic cleanup exists. This is a **ghost booking** scenario.                                                                                                                      |
| **Recommended Fix** | 1. Create a periodic job (e.g., every 5 minutes) that scans for PENDING bookings older than 15 minutes without a corresponding active timeout job, and triggers compensation. 2. Move the timeout job creation inside the Prisma $transaction or use a separate database-backed scheduler.                                                                     |

### RISK 4: Stripe Webhook Produces Directly – No Deduplication

| Attribute           | Value                                                                                                                                                                                                                                                                                                                                                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🔴 HIGH**                                                                                                                                                                                                                                                                                                                                                          |
| **Evidence**        | `apps/payment-service/src/routes/webhooks.route.ts:37-101` – The webhook handler extracts `bookingId` from metadata. If Stripe retries the webhook (which it does with exponential backoff), the handler will `producer.send()` again with the same bookingId. No `eventId` is checked for dedup before Kafka send.                                                  |
| **Impact**          | If the booking service processes both duplicate events, the `processed_events` table will catch the second attempt (ON CONFLICT DO NOTHING). However, this creates unnecessary processing. More critically, if the first send fails and Stripe retries after the booking-events worker already partially processed the booking, it could lead to inconsistent state. |
| **Recommended Fix** | Use Stripe's `idempotency_key` header (passed as `Idempotency-Key`) to deduplicate webhook events. Add a webhook event log table to track processed webhook event IDs.                                                                                                                                                                                               |

### RISK 5: Shared Database – No Service Isolation

| Attribute           | Value                                                                                                                                                                                                                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🟡 MEDIUM**                                                                                                                                                                                                                                                                                  |
| **Evidence**        | Both `apps/booking-service/` and `apps/payment-service/` import from `@repo/product-db` (same Prisma client, same PostgreSQL database). The Booking entity has foreign keys to `User` and `Hotel` tables, meaning a schema migration in one service requires coordination across all services. |
| **Impact**          | Schema changes require synchronized deployments across all services. A breaking change to the `Booking` table structure could break the Payment Service's `updateBookingStatusToPaid()` function.                                                                                              |
| **Recommended Fix** | Long-term: migrate to database-per-service pattern. Each service own its data. Short-term: enforce strict API boundaries – Payment Service should call Booking Service's API to update booking status, not directly modify the database.                                                       |

### RISK 6: Email Sent via Direct HTTP (Bypasses Kafka)

| Attribute           | Value                                                                                                                                                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🟡 MEDIUM**                                                                                                                                                                                                                                             |
| **Evidence**        | `apps/booking-service/src/queues/booking-events.queue.ts:100-104` – Email confirmation is sent via `fetch("http://localhost:8003/send-confirmation", ...)` directly from the BullMQ worker. This is fire-and-forget with `.catch()` that swallows errors. |
| **Impact**          | If the email service is down, the confirmation email is silently lost. The user won't receive their booking confirmation despite payment being successful. No retry mechanism exists for this path.                                                       |
| **Recommended Fix** | Use the existing outbox pattern: write an outbox event for email sending in the same transaction as the booking confirmation. Or, use the Kafka `email-events` topic that the Email Service already consumes.                                             |

### RISK 7: No Payment Refund on Cancellation

| Attribute           | Value                                                                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🔴 HIGH**                                                                                                                                                                                                                                 |
| **Evidence**        | A search for "refund", "stripe.refund", "cancelPayment" in the codebase returns no results. The saga timeout and payment failure compensations only update booking status to CANCELLED – no Stripe refund or payment reversal is initiated. |
| **Impact**          | If a booking is paid (CONFIRMED) and then cancelled (e.g., hotel not available, admin cancellation), no refund is issued to the customer. This is a critical business and legal issue.                                                      |
| **Recommended Fix** | Add payment reversal logic to the compensation handlers. For Stripe payments, call `stripe.refunds.create({ paymentIntent: paymentIntentId })` during cancellation. Add a BullMQ queue for delayed/idempotent refund processing.            |

### RISK 8: Overbooking Potential (Race Condition)

| Attribute           | Value                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🟡 MEDIUM**                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Evidence**        | `apps/booking-service/src/utils/booking.ts:61-68` – The double-check for conflicting bookings uses `prisma.booking.findFirst()` with `status: ["CONFIRMED", "PENDING"]`. However, the redlock TTL is 10 seconds while the Saga timeout is 15 minutes. The lock is released right after booking creation (`utils/booking.ts:196-203`).                                                                                                     |
| **Impact**          | If two users book the same dates nearly simultaneously, the first acquires the lock and creates a PENDING booking. The second user's POST fails (lock held). But if user 1's payment fails after 14 minutes, the booking is cancelled. User 2 retries and succeeds. However, if user 1's payment succeeds just as user 2 creates a new booking, both could become CONFIRMED during the window between payment success and booking update. |
| **Recommended Fix** | The current Redis hold mechanism partially mitigates this (10-minute hold). However, add a payment-time check: when processing PAYMENT_SUCCESS, re-verify availability before confirming (the booking-events worker already does this partially). Consider tightening the booking conflict check to include a broader time window.                                                                                                        |

### RISK 9: Processed Stale Messages in Outbox

| Attribute           | Value                                                                                                                                                                                                                                                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🟡 MEDIUM**                                                                                                                                                                                                                                                                                                                |
| **Evidence**        | `apps/booking-service/src/workers/outbox-worker.ts:33-46` – The `claimPendingMessages` function claims messages with `status: "PROCESSING"` in a transaction. However, there is no recovery mechanism for messages stuck in PROCESSING state (if the worker crashes mid-processing). These messages will never be published. |
| **Impact**          | If the Outbox Worker crashes after updating status to PROCESSING but before `producer.send()`, the event is permanently stuck. Booking created events, cancellation events – all stuck.                                                                                                                                      |
| **Recommended Fix** | Add a periodic job to detect PROCESSING messages older than N seconds (e.g., 60s) and reset them to PENDING. Implement the claim-check pattern properly with a heartbeat.                                                                                                                                                    |

### RISK 10: Dead Code – `sendBookingEvent` with Incorrect API

| Attribute           | Value                                                                                                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Severity**        | **🟢 LOW**                                                                                                                                                                                                                                                   |
| **Evidence**        | `apps/payment-service/src/utils/kafka.ts:16-26` – The `sendBookingEvent` function is defined but never called anywhere in the codebase. It passes arguments in wrong format (`producer.send(topic, messages[])` vs correct `producer.send(topic, message)`). |
| **Impact**          | None currently – dead code. But if someone uses it in the future, it will fail with incorrect arguments.                                                                                                                                                     |
| **Recommended Fix** | Remove the dead function, or fix it to match the actual producer API in `packages/kafka/src/producer.ts`.                                                                                                                                                    |

### RISK 11: Dual Database Inconsistency

| Attribute           | Value                                                                                                                                                                                                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Severity**        | **🟡 MEDIUM**                                                                                                                                                                                                                                                                                                               |
| **Evidence**        | `packages/booking-db/src/booking-model.ts` (MongoDB) and `packages/product-db/generated/prisma/models/Booking.ts` (PostgreSQL) define overlapping Booking models. The analytics cron (`apps/booking-service/src/cron/analyticsJob.ts:62`) queries MongoDB `Booking.aggregate()`, while core business logic uses PostgreSQL. |
| **Impact**          | The analytics daily stats are based on MongoDB data, while business logic runs on PostgreSQL. If there's data drift between the two databases (which is likely since new bookings are written to PostgreSQL only), the analytics will be incomplete.                                                                        |
| **Recommended Fix** | Migrate analytics to use PostgreSQL exclusively. Remove the MongoDB dependency once legacy data is migrated. The `@repo/booking-db` package should be deprecated.                                                                                                                                                           |

## 9. FINAL VERDICT

### Architecture Classification: **HYBRID (Choreography-dominant)**

The Stazy Hotel system is a well-intentioned event-driven microservices architecture with several commendable patterns:

- ✅ Transactional Outbox with claim-check processing
- ✅ Multi-layer idempotency (in-memory + database unique constraints)
- ✅ Redis-based room hold + Redlock for concurrency
- ✅ BullMQ saga timeout with compensation
- ✅ Retry with exponential backoff across all queues
- ✅ Dead Letter Queues for failed payment and email jobs

### Critical Issues Requiring Immediate Attention:

1. **🔴 Stripe webhook bypasses outbox** – single biggest data loss risk
2. **🔴 In-memory idempotency not suitable for production** – breaks with multiple instances
3. **🔴 No payment refund logic** – legal/compliance risk for paid cancellations
4. **🔴 Missing timeout job recovery** – ghost bookings from service crashes
5. **🟡 Shared database coupling** – prevents independent service evolution
6. **🟡 Email sending bypasses Kafka** – non-retryable, silent failures
7. **🟡 Dual database with data drift risk** – MongoDB vs PostgreSQL inconsistency

### Recommended Architecture Evolution:

1. **Bootstrap Period (Immediate):**
   - Route Stripe webhooks through the outbox pattern
   - Implement Redis-based distributed idempotency
   - Add stale PROCESSING message recovery for outbox
   - Add periodic PENDING booking cleanup job

2. **Growth Phase (1-3 months):**
   - Add refund logic to compensation handlers
   - Implement database-per-service for Booking and Payment services
   - Add webhook event log table with idempotency
   - Migrate analytics from MongoDB to PostgreSQL

3. **Scale Phase (3-6 months):**
   - Consider introducing a formal Saga Orchestrator (e.g., Temporal) for complex workflows
   - Implement CQRS with read replicas for analytics queries
   - Add event sourcing for booking lifecycle audit trail
   - Introduce schema registry for Kafka events

The system demonstrates strong fundamentals with the outbox pattern, Redis locking, and BullMQ retry architecture. Addressing the critical gaps identified above will transform it from a well-designed academic project into a production-grade event-driven microservices platform.
